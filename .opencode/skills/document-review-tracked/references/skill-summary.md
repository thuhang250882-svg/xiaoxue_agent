### 与普通 AI 改稿工具的本质区别

普通 AI 改稿 = 给你一份新文档，你不知道改了哪里、为什么改
花叔审稿 = **在原文上留下批注气泡 + 红色修订痕迹**，打开 Word 就是熟悉的「审阅模式」

## 二、解决的三大长期痛点

| 痛点 | 传统做法 | 花叔的方案 |
|------|---------|-----------|
| AI 改稿来回粘贴导致 Word 格式炸裂 | 复制→粘贴→ChatGPT→粘回 | 直接改 docx XML，原格式 100% 保留 |
| 律师/老板要的是「哪里改了为什么改」 | AI 只给改完的新文档 | 输出标准 `<w:ins>` `<w:del>` 修订标签 + `<w:comment>` 批注节点 |
| 合同/内部方案/报价单不能上云 | 不敢用 AI | 直接在本地文件上操作，文档不离开电脑 |

## 三、三种审稿模式

### 1. 合同审查模式（contract）

**适用场景**：商业合同、采购合同、销售合同、NDA、劳动合同

**审查关注点**：

| 审查维度 | 具体检查内容 |
|---------|------------|
| 金额条款 | 币种是否明确、含税口径、计算方式 |
| 付款条件 | 账期是否合理、违约责任是否对等 |
| SLA 量化 | 可用性指标 + 违约赔偿条款 |
| 保密条款 | 义务范围 + 保密期限是否完整 |
| 争议解决 | 管辖法院 / 仲裁机构是否清晰 |
| 公文规范 | 不规范表述（如「根据」→「依据」） |

### 2. 报告改稿模式（report）

**适用场景**：商业报告、内部报告、白皮书、调研报告

**审查关注点**：

| 审查维度 | 具体检查内容 |
|---------|------------|
| 数据准确性 | 出现需要核对的数据时标记提示 |
| 表述歧义 | 一句话有多种理解时标出 |
| 逻辑跳跃 | 前后段论证不连贯 |
| 用词专业度 | 口语化或表述模糊时建议替换 |
| 结构均衡 | 章节篇幅差异过大时提示 |

### 3. 方案评审模式（proposal）

**适用场景**：项目方案、产品 PRD、运营方案

**审查关注点**：

| 审查维度 | 具体检查内容 |
|---------|------------|
| 目标/手段对齐 | 声称的目标和实际方法是否匹配 |
| 假设暴露 | 隐含假设是否清晰列出 |
| 风险盲点 | 重要风险是否被回避或低估 |
| 可执行性 | 步骤是否具体到能落地 |
| KPI 与时间表 | 是否量化、是否有明确里程碑 |

## 四、标准工作流

```
用户提交 .docx 文件 + 指定模式（或自动判断）
          │
          ▼
┌──────────────────────────┐
│ 1. 接收任务               │  .docx 文件 + 模式（未指定则按内容关键词自动判断）
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│ 2. 读取文档结构           │  解析每一段的 ID、文本、样式 → 段落列表
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│ 3. 模型判断               │  每段过审稿模型 → 输出结构化 JSON 决策列表（不是新文档）
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│ 4. 代码注入               │  遍历 JSON → 注入 word/comments.xml（批注）
│                          │              + word/document.xml（修订）
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│ 5. 输出新文件             │  <原文件名>.reviewed.docx（原文件不覆盖）
└──────────────────────────┘
```

### 工作流的关键设计

1. **模型与代码职责分离**：模型只做判断（输出 JSON），代码做所有文档操作
2. **不生成新文档**：在原文档 XML 上追加批注和修订节点
3. **原文件保护**：输出 `.reviewed.docx`，永不覆盖原文件
4. **大文档分段**：超过 10000 字时分段处理，最终统一写入

## 五、核心工程哲学：让模型做判断，让代码做操作

这是本专家**最核心的设计决策**，也是其他智能体最值得学习的设计理念。

### Agent 型 vs 工具型对比

| 维度 | Agent 型（差） | 工具型（花叔的方案，好） |
|------|--------------|----------------------|
| **模型的活** | 让模型「写出修改后的文档」 | 让模型只输出结构化 JSON |
| **定位的活** | 让模型决定批注插入位置 | 代码做精确字符串定位 |
| **格式的活** | 让模型保留 Word 格式 | 代码直接改 OOXML，格式不会动 |
| **失败模式** | 模型一跑偏整篇炸 | 代码原子化操作，可回滚 |

### 为什么这样设计

1. **轻量模型也能稳定跑**——模型不需要理解 OOXML 格式，只需要判断"这段文字有没有问题"
2. **规避「Agent 一跑偏整篇炸」**——代码做原子化操作，每条独立执行，互不影响
3. **格式零风险**——代码直接操作 XML 节点，不经过模型的"理解→重写"过程

### JSON 决策列表设计

模型输出的不是修改后的文档文本，而是结构化的决策列表。每条决策包含：
- 段落定位信息（match_text）
- 批注内容（这里有什么问题、为什么要改）
- 修订建议（建议怎么改）
- 严重等级（CRITICAL / WARNING / INFO）

代码拿到 JSON 后，通过精确字符串匹配在段落中定位，然后注入对应的 XML 节点。

## 六、三层失败保护

这是保证"永远不会整篇翻车"的关键机制：

| 层级 | 机制 | 说明 |
|------|------|------|
| **第 1 层** | JSON Schema 强校验 | 模型输出必须符合固定 schema，不符合自动重试（最多 3 次） |
| **第 2 层** | 字符串精确匹配 | 不靠模型「知道位置」，靠 `match_text` 在段落里查找 |
| **第 3 层** | 单条失败隔离 | 某条批注匹配不到 → 跳过并记录，不影响其他批注 |

### 降级策略

- **最差情况**：只保留能匹配成功的那些批注
- **永远不会**：因为一条批注失败导致整篇文档损坏
- **可回滚**：代码原子化操作，每一步都可以回滚

---

## 七、OOXML 技术架构

### 输出的 Word XML 元素

| XML 元素 | 作用 | 对应 Word 效果 |
|---------|------|--------------|
| `<w:comment>` | 批注节点 | 右侧批注气泡，显示审稿意见 |
| `<w:ins>` | 插入修订 | 红色下划线文字，表示建议新增 |
| `<w:del>` | 删除修订 | 红色删除线，表示建议删除 |

### 用户在 Word 中看到的效果

- 打开 `.reviewed.docx` → 自动进入「审阅模式」
- 右侧批注气泡显示每条审稿意见
- 红色删除线 + 红色新字显示修订建议
- 用户可逐条「接受」或「拒绝」修订
- 所有「删除」都是修订标记，原文内容未被真正删除

## 八、输出规范

### 交付物（两件套）

| 交付物 | 说明 |
|--------|------|
| **`<filename>.reviewed.docx`** | 原文 + 全部批注和修订痕迹，可直接在 Word 里打开 |
| **审稿摘要** | 告诉用户「加了 N 条批注，其中 X 条 CRITICAL；做了 M 处修订；建议优先处理 P1、P3」 |

### 摘要内容规范

- 批注总数 + 按严重等级分布（CRITICAL / WARNING / INFO）
- 修订总数
- 优先处理建议（指出最重要的几条）
- 原文件未被修改的确认

## 九、核心规则与约束

### 不可违反的规则

| 规则 | 说明 |
|------|------|
| **只处理 .docx** | 不支持 .doc / .pdf / .txt，需提示用户先转换 |
| **不删除原文内容** | 所有「删除」都是修订标记，用户可一键拒绝 |
| **不上传云端** | 任何情况下都不会把文档发到云端，全程本地操作 |
| **原文件不覆盖** | 输出 `.reviewed.docx`，原文件保持不变 |
| **大文档分段** | 超过 10000 字时分段处理，最终统一写入 |

### 可配置项

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 批注作者署名 | 「花叔 AI 审稿」 | 可在调用时通过参数覆盖 |
| 审稿模式 | 自动判断 | 可手动指定 contract / report / proposal |

## 十一、设计哲学（给其他智能体的核心启示）

### 1. 审稿人留下的不是改后的文档，是审议的痕迹

> 一份合同你签字之前，律师告诉你「这条改了字号」是没用的，他要告诉你「这条原话有歧义、所以建议改成 XX」。

这是本专家的核心信念。AI 审稿的价值不在于"给你一份新文档"，而在于**告诉你哪里有问题、为什么有问题、建议怎么改**——和人类律师/审稿人留下同样格式的痕迹。

### 2. 让模型做判断，让代码做操作

这是最值得其他智能体学习的设计模式：
- **模型擅长的事**：理解语义、判断问题、生成建议
- **代码擅长的事**：精确定位、格式操作、原子化执行
- **分离的好处**：各司其职，失败隔离，轻量模型可用

### 3. 三层失败保护——永远不会整篇翻车

从 Schema 校验到字符串匹配到单条隔离，每一层都是独立的安全网。最差降级为"只保留能成功的批注"，但永远不会损坏原文档。这种**防御性设计**值得所有需要操作文件的智能体学习。

### 4. 本地优先——敏感文档不上云

合同、内部方案、报价单这类高敏文档，用户不敢用 AI 的核心顾虑是数据泄露。全程本地操作、文档不离开电脑，是赢得用户信任的基础。

### 5. 原格式零破坏

通过直接操作 OOXML 而非"理解→重写"的方式，保证原文档的格式（字体、样式、表格、图片）100% 保留。这解决了 AI 改稿"格式炸裂"的长期痛点。

### 6. 模式驱动的专业化审查

三种模式各有专属的审查关注点，不做"万能通用"的模糊审查。合同模式关注金额条款和 SLA，报告模式关注数据准确性和逻辑连贯，方案模式关注目标对齐和可执行性。这种**场景化专业分工**让审查更有深度。
