# 环节 4：权限矩阵设定规则

## 现状声明

系统当前为**单机受控目录模型**（无多用户 RBAC）。本矩阵先把角色落到**流程与留痕**上，待多用户版本上线后映射为系统权限。技术侧已固化的防线：

- 路径信任锚：智能体只能导入用户消息中逐字出现的路径
- 管理目录边界：索引/删除操作不得越出 `knowledge/` 目录
- SHA256 完整性：同内容防重复、归档版本防静默复活
- HTTP API 401 鉴权：未授权访问拒绝

## 角色与权限矩阵

| 操作 | 提交人（业务部门） | 审核人（知识管理员） | 发布人（部门负责人） | 系统防线 |
|------|:---:|:---:|:---:|---------|
| 收集登记资料 | ✅ | ✅ | — | 来源授权红线（环节1） |
| 格式审核 | ❌ | ✅ | — | 支持矩阵+审核清单（环节2） |
| 分类判定 | 建议 | ✅ 终审 | — | 七分类枚举+判定顺序（环节3） |
| 执行 import 入库 | ❌ | ✅ | — | knowledge_manage 受控通道 |
| 扫描件 OCR 处理 | ❌ | ✅ | — | pdfkit --ocr_fallback 两步入库 |
| 上架发布（对外可见） | ❌ | 建议 | ✅ 审批 | 发布审批机制（环节5） |
| 版本更新 update | 提出 | ✅ 执行 | 知会 | 旧版自动归档+版本号递增 |
| 删除下架 remove | ❌ | 提出 | ✅ 审批 | 双重确认（sourceId 明示+用户确认） |
| 检索查询 | ✅ 全员 | ✅ | ✅ | knowledge_search 只读 |

## 设定规则

1. **提交人不得自己审核自己**：提交→审核必须换人（单人场景下由提交部门负责人兼审核人时，须在留痕中注明）。
2. **发布与审核分离**：审核人执行入库，发布人决定可见性；confirm 模式下两步合一但留痕分列。
3. **最小权限**：业务部门默认只有"提交+检索"两条通道；导入、更新、删除操作集中在审核人。
4. **留痕即证据**：每次权限敏感操作（import/update/remove）记录操作人、时间、sourceId——入库回执自动携带。
5. **涉密隔离**：密级资料不进本知识库，走涉密渠道；审核人发现密级标识立即中止流程并报告。
