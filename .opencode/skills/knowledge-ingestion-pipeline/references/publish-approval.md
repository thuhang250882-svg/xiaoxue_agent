# 环节 5：上架发布审批机制

## 审批链（标准路径）

```
提交（业务部门）→ 格式+分类审核（知识管理员）→ 入库执行（审核人）
→ 发布审批（部门负责人）→ 上架生效 → 留痕归档
```

单人/小团队简化路径：提交与审核同人时，**入库前向用户展示审核结论并取得确认**（confirm 模式），确认记录即为审批留痕。

## 发布模式

| 模式 | 行为 | 适用 |
|------|------|------|
| confirm（默认） | 审核结论展示给提交人确认后入库，即时可检索 | 常规资料 |
| draft | 入库为草稿事实卡/归档，不进检索索引 | 高风险、待复核资料 |

## 上架前最终检查（全通过才发布）

- [ ] 环节 1-4 交付物齐全（登记表/审核结论/分类记录/审批链）
- [ ] `knowledge_manage list` 能看到该记录，`active: true`
- [ ] 扫描件：`textPath` 存在且内容可检索（抽 1 个关键词实测命中）
- [ ] 大文件：`paragraphCount > 0`
- [ ] 标题符合命名规范（环节 3）
- [ ] 免责声明已附（引用条款时以正式发布版本为准）

```
- SHA256: e72a4a...（完整性校验值）
- 段落数: 96 | OCR: 是（84 页扫描件，RapidOCR）
- 审批链: 提交人→审核人→发布人（见审批链签署记录）
```

## 版本与下架规则

- **更新**：新文件 `update` 后旧版自动归档（`_archive/`），版本号 +1，`supersedes` 指向旧版；旧版不可再作为新资料导入（防复活）。
- **下架**：删除需发布人审批 + 用户对 sourceId 明确确认后才执行 `remove`；删除后原件与 OCR 副本同时清理。
- **回滚**：误删/误更正通过重新导入原文件恢复（SHA256 去重会让历史版本直接复活为活跃记录，需审核人确认）。

## 留痕归档位置

Obsidian 协作目录：`06-日常工作管理/智能体协作/YYYY-MM-DD-〔资料名〕-入库审批.md`，含五环节全部交付物。
